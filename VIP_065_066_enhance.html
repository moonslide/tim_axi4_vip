1. BENCH-065 — CPU-replacement AXI master lacks programmable legal mid-burst RREADY backpressure

1.1 Problem summary

Per BENCH-065_soc01_cpu_axi_midburst_rready_stimulus_missing.md ("The defect"), the shared master BFM exposes no supported control to select an internal read-burst beat and hold RREADY=0 for a specified number of clocks. The transaction-level r_wait_states applies only in front of beat 0; once a burst is partially collected the BFM keeps RREADY asserted unless the completed-response queue is full. Consequently a green burst read "does not establish that the target memory/bridge holds its response correctly when this CPU-replacement master deliberately stops accepting data between beats". The record grades this as STATIC OBSERVED for the code facts, INFERRED for "the supported API cannot select a legal internal-beat pause", and UNSETTLED for any runtime impact or masked DUT defect. It is a capability gap, not a VIP correctness bug, and not an RTL defect.

1.4 Recommended option and rationale

Option A, with Option B recorded as a possible later addition for SoC-level "hold now" use if the SoC owners need it. Rationale:

  • Follows the existing architecture. The BFM comment at 414–418 already says the delay "travels with the request" and is "queued into ar_outstanding_q at the handshake"; the B channel does the same. Option A extends that record with a position, instead of introducing a second, out-of-band control path.
  • Matches the reference-VIP precedent. The SVT user guide models response timing as per-beat arrays on the transaction object (e.g. rvalid_delay[], rresp[]) rather than as a single first-beat scalar (…/how_to_provide_data_response_information_to_slave_after_time_delay.html). A transaction-scoped, beat-indexed construct is the industry-normal way to express "stall at beat k". The SVT suspend_awready live-hold (…/wait_state_mechanisms.html) shows the port-level alternative is also legitimate — that is why Option B is kept as a candidate, not discarded.
  • Deterministic and per-transaction, which is what BENCH-065 acceptance items 2–3 require ("check first/middle/final-beat positions separately"; "for multiple IDs, account per transaction rather than by total bus beats"). Option B can only stall "the port at time t".
  • Zero-stall and first-beat semantics preserved (acceptance item 1) because the new descriptor defaults to "no stall" and the beat-0 branch is not rewritten.

1.5 Design outline (structural — no code)

  1. Transaction descriptor (master/axi4_master_tx.sv): a new, non-randomized-by-default stall specification for read data acceptance. Minimum form: a beat position and a cycle count. Preferred form, mirroring the SVT per-beat array precedent: a dynamic array of per-beat RREADY wait states whose element 0 is defined to alias the existing r_wait_states so no existing constraint, printer or monitor field changes meaning. Empty array = current behaviour. A soft constraint keeps the array empty unless a sequence sets it, so no regression's randomization changes.
  2. Outstanding-read record (…driver_bfm.sv:440–443, ar_outstanding_s): carry the descriptor alongside r_wait_states, copied at the same AR handshake point where r_wait_states is queued today. Nothing about entry creation/deletion, ar_issued_cnt, r_burst_cnt, or the credit path changes.
  3. R-channel task (…driver_bfm.sv:560–575): today the RVALID-not-yet-accepted branch forces zero delay when r_accum_q.exists(rid). The change is to replace that forced zero with a lookup: "beats already accepted for this RID" (from the accumulator's beats) indexes the descriptor of the oldest outstanding entry for this RID; the resulting count is loaded into the existing r_wait_cnt/r_wait_armed mechanism, which then behaves exactly as it does for beat 0 (registered RREADY, count down, assert at zero). No new counters; the existing arm/disarm points (556–558, 577–579) already reset state after each handshake.
  4. Default-ready function (…driver_bfm.sv:481–485): unchanged in ordering. The mid-flight "return 1" remains the idle value; the stall is spent only in the RVALID branch, so a stall can never be applied when no beat is offered (no dead cycles added to an idle bus).
  5. Bound on stall length: the descriptor's cycle count is capped by a named agent-config limit that is strictly below the R-claim escape timeout (the 50 000-cycle bound referenced in landmine #37) so that a legal stall cannot be mistaken for the abandoned-burst failure. Acceptance item 2 requires "stall duration below any declared response-bound policy unless testing that policy explicitly" — this cap is that declaration.
  6. Pin-level witness (agent/master_agent_bfm/axi4_master_monitor_bfm.sv + the VIP's master covergroups): a per-transaction record of "RVALID===1 && RREADY===0 observed after ≥1 accepted beat and before RLAST for this RID", with the stall length and the beat position at which it occurred, and a coverage point over {first, middle, final} positions. This is new sampling of existing wire state; it does not gate or alter the driver. Zero hits must read as unexercised, per acceptance item 4.
  7. Directed sequence + test: a new master sequence issuing an INCR read with ARLEN ≥ 3, descriptor set for each of the three positions, plus a no-stall control run of the same sequence; a checker (scoreboard or SVA in assertions/master_assertions.sv) that during the stall requires stable RDATA/RRESP/RID/RLAST and held RVALID, then exactly ARLEN+1 beats and correct final RLAST for that transaction. Test registered in testlists/axi4_transfers_regression.list for all three bus modes.
  8. Shared-RREADY policy (explicit, documented): when a beat of a different RID is presented while a stall for RID r is being spent, RREADY stays low for that beat too — AXI permits a master to deassert RREADY at any time, so this is protocol-legal; the witness and beat accounting are per-transaction so the interleaved burst is neither counted as stalled nor lost. This is the same trade-off the existing "Known limit" comment already accepts in the opposite direction. The alternative (defer the stall until the presented beat belongs to r) is listed as an open question in Section 5 because the master cannot influence which RID the subordinate presents.
  9. SoC propagation (out of this repo): the SoC environment's SOC01_RDY_BP-style knob mapping and burst-sequence API gain a way to populate the descriptor. Not part of the VIP change; called out so the BENCH-065 "propagated through the SoC API/config" clause is not silently dropped.

1.8 Rollback plan

  • The change is additive: an empty descriptor reproduces today's behaviour. First-line rollback is therefore configuration: forbid non-empty descriptors via the agent-config cap (set to 0) without touching the BFM.
  • Source rollback: revert the BFM R-task branch and the ar_outstanding_s field in one commit, keeping the tx field and monitor witness (harmless when never populated) if desired, or revert all three. Do not partially revert the R task while leaving the struct field populated.
  • Re-run the same baseline sample + run_fabric_smoke.sh after rollback; the directed test returns to its fail-before signature and must be de-registered or marked expected-fail, never left silently red.

2. BENCH-066 — Basic X-injection request cleared before driver consumption

2.1 Problem summary

Per BENCH-066_x_injection_flag_cleared_before_item.md (Summary; Section 1), the basic master X-injection sequences set a wildcard uvm_config_db flag, sleep a fixed #(x_inject_cycles * 10ns), clear the flag, re-arm assertions, and only then submit their recovery item; the driver proxy reads the flag only after get_next_item() returns. With an idle driver and no concurrent traffic during the flag window, the sequence's own item arrives after the flag is already 0 and the BFM's X-drive task is never called. The record grades the ordering as MEASURED (static), "isolated execution skips the intended BFM call" as INFERRED, and the dynamic behaviour, concurrency effects and per-signal recovery as UNSETTLED. Its supported conclusion is narrow: "the basic sequence does not reliably synchronize its injection request with its own traffic" — it is not a claim that every regression has zero X activity.

2.4 Recommended option and rationale

Option B for transaction-triggered injection, plus Option C for idle injection, with the wildcard config_db flags retired (or, during transition, retained only as a read-only mirror the assertion gate no longer depends on). Rationale:

  • It removes the root cause by construction. The SVT reference attaches error injection to the transaction object itself (svt_axi_transaction_exception / …_exception_list, populated inside a svt_axi_master_callback::post_input_port_get() callback, …/verification_features/error_injection.html): injection fires exactly when that transaction is processed by that agent, with no async flag and no sleep timer racing item delivery. Option B is the same shape using this VIP's existing tx/proxy/BFM layering. The record's own repair-contract item 2 ("arm before the relevant item reaches the consumer and keep the request valid until consumption is acknowledged") is satisfied trivially when the request is the item.
  • Scoping and ownership come for free (contract item 4): the descriptor rides on an item delivered to one sequencer → one proxy → one BFM. No other master can consume it; no shared duration variable exists.
  • Acknowledgement is native (contract item 3): the item's status fields are written by the BFM in aclk terms, so "duration follows observed clock edges" (repair-matrix row 5) is inherent and the 10ns assumption disappears from the sequence.
  • Idle mode needs C (contract item 2, second sentence; matrix row 3): AWVALID idle injection and the virtual flag-only sequences have no item, so a transaction descriptor cannot carry them. A dedicated, agent-scoped call is the smallest honest mechanism.
  • Assertion policy becomes explicit (contract item 6): the gate x_inject_mode should be derived from a BFM-owned "injection in progress on this interface" state (raised when the BFM starts driving X, lowered when it restores the signal), not from the request flag. That closes the window on both sides and makes "assertion-detection self-test keeps its target assertion armed" a matter of the test not requesting suppression, rather than of $assertoff wildcards.

2.5 Design outline (structural — no code)

  1. Descriptor on the transaction (master/axi4_master_tx.sv): target-signal enum (NONE / AWVALID / AWADDR / WDATA / ARVALID / BREADY / RREADY), cycle count, mode enum (PRE_TRANSACTION = today's "drive X, restore, then dispatch the item" hook; ACTIVE_PHASE = X overlapping the item's own VALID/READY phase, to be advertised per signal only where the BFM implements it), and status fields written back by the driver: accepted/started/completed flags with aclk-cycle stamps, plus a result code (OK / TIMEOUT / ABORTED_BY_RESET). Default NONE: no behavioural change for any existing item.
  2. Proxy consumption (master/axi4_master_driver_proxy.sv:358–420, 893–922): the six flag-read blocks are replaced by one descriptor dispatch on the item just obtained. The proxy no longer reads or writes the wildcard keys. The write task handles AW/W/B targets, the read task AR/R targets; a descriptor naming a signal of the other channel is a sequence error reported once, not silently ignored.
  3. BFM task contract (…driver_bfm.sv:1022–1146): existing per-signal tasks keep their drive semantics but gain (a) a status return so the proxy can stamp accept/start/complete, (b) an interface-level "X drive in progress" state bit per channel (generalising the existing bready_x_inject_active / rready_x_inject_active ownership hand-off to AW/W/AR), and (c) a reset/abort path that restores the signal to its idle value and clears the state bit. This is the "restore signal ownership on completion, timeout, reset and sequence abort" requirement (contract item 7).
  4. Idle-injection path (Option C): an agent-scoped request object (obtained via the agent's config object / proxy handle, not a "*" key) with the same descriptor and status shape, serviced by a proxy thread that runs alongside the item loops and acquires the channel's ownership bit before calling the BFM. The virtual flag-only sequences and inject_x_on_awvalid migrate to it.
  5. Assertion gating (assertions/master_assertions.sv:389–433): x_inject_mode derived from the BFM's per-channel "X drive in progress" state (exposed on the interface the assertions module already binds to), replacing the six-key config_db poller. The disable iff terms on 417/427 stay as written; only their source changes. The sequence-level $assertoff/$asserton wildcards (390–404) are removed from the basic sequences; a test that wants a check suppressed asks for it explicitly through the descriptor's assertion-policy field (SUPPRESS_DURING_INJECTION / KEEP_ARMED), so the assertion-detection self-test can keep its target armed (matrix row 9).
  6. Witness (assertions/master_assertions.sv:436–448, X_INJECT_MONITOR): split the aggregated counter into per-signal counters, attributed to interface instance and to the descriptor that requested the drive (by the accepted/started stamps), so the log line can state "X on AWADDR, master N, cycles a–b, requested by item id X". This is what the record's Section 3.3 requires before a monitor message can count as evidence.
  7. Sequence rewrite (seq/master_sequences/axi4_master_x_inject_seq.sv): each basic task becomes "build the injection item (descriptor set) → start/finish → inspect status → build the recovery item (descriptor NONE) → start/finish → run the recovery checks". Injection and recovery are separate items (contract item 5). No sleeps.
  8. Out of scope, explicitly: the active/random family and its orphaned key (BENCH-040) and the slave-side injectors are not changed; their disposition must be recorded separately (record Section 7, fourth bullet).

2.7 Verification plan

  1. Fail-before. Add the per-signal witness/checker first and run the isolated basic AWADDR case (one active master, no background traffic, valid responder, bounded timeout — record §5 "Minimal isolated reproduction") on the unmodified VIP.   2. Pass-after. For the assertion-detection self-test the expected failure signature and the harness verdict are recorded separately; a zero-error PASS is not the verdict for that case.
  3. Repair matrix. Every row of the table in 2.6 gets a named run with log/FSDB path, or an explicit "not advertised / not supported" entry. No row is inferred from another.
  4. Baseline regression sample (Iron Rule 2). BFM and proxy are both touched, so the 12+ test baseline sample from TRACKB_DEBUG_NOTES.md and sim/run_fabric_smoke.sh (3/3 PASS) are mandatory before any claim; include axi4_error_inject_rready_x_test, axi4_error_inject_rready_random_test, and the virtual error-inject tests already registered. Run via axi4_regression.py --lsf.
  5. Registration. Any new or renamed test in testlists/axi4_transfers_regression.list (all three bus modes); the smaller sim/axi4_transfers_regression.list only if intended.
  6. Disposition record. The record's Section 7 deliverables (patch explanation, isolated evidence, matrix results, active/random/slave-family disposition, remaining limitations) go into the fresh tracking doc of Section 3; BENCH-040 is not touched or closed by this work.

2.8 Rollback plan

  • Descriptor default NONE means the tx-side addition is inert; the behaviour-changing pieces are the proxy dispatch, the BFM status/ownership additions, the assertion-gate source, and the sequence rewrite. Revert those four in one commit (they are only meaningful together); leave or revert the tx field as a separate decision.
  • If only the assertion-gate change regresses (e.g. a test that relied on the flag-driven suppression window now fires NO_HANDSHAKE_DURING_X), that is a finding about the test, not grounds to restore the poller; record it, then decide.
  • After any rollback re-run the same baseline sample + run_fabric_smoke.sh, and mark the new directed tests expected-fail or de-register them explicitly.

5. Open questions and approval gate

Approval gate BENCH-065 and BENCH-066 are both Open, Medium-severity, unassigned dispositions in VIP_ISSUES.md. Per this project's governance, implementation of either may begin only after a human reviews this plan, chooses the option, assigns an owner, and confirms the verification/rollback plan. This document is the proposal, not the authorization.

Genuinely open design questions

  1. Shared RREADY under interleaved read data (BENCH-065, record "Blast radius" and BFM "Known limit"). While a stall for RID r is being spent, a beat of RID s may be presented. Two legal policies: (a) stall it too — simple, deterministic, protocol-legal, but s experiences an unrequested stall; (b) defer r's stall until a beat of r is actually presented — never touches s, but the stall may then land at a different absolute time and, if the subordinate finishes s first, effectively at a later beat of r only if the descriptor is re-evaluated per beat. This plan proposes (a) with per-transaction accounting; the reviewer must confirm, because the SoC CPU-replacement use case may be single-ID and (a) may be all that is needed.
  2. Descriptor shape (BENCH-065). Scalar pair (position, cycles) versus per-beat array with element 0 aliased to r_wait_states. The array follows the SVT precedent and future-proofs multi-stall bursts; the pair is smaller. Reviewer's call.
  3. Stall cap value and its relation to the claim-task escape. The cap must be below the 50 000-cycle bound; the precise value and whether it is per-agent config or a compile-time parameter is open.
  4. Which signals may advertise ACTIVE_PHASE (BENCH-066). Today's BFM tasks are idle/pre-transaction drives. Implementing X during an item's own VALID/READY phase is new BFM behaviour per signal; the reviewer should decide whether ACTIVE_PHASE is in this repair's scope or recorded as "not advertised" per matrix row 4.
  5. Transition policy for the wildcard config_db keys (BENCH-066). Remove outright, or keep as read-only mirrors for one release so external sequences (SoC-side) do not break silently. Removal is cleaner; a mirror risks recreating the very race being fixed.
  6. Where the reset/abort path lives (BENCH-066 contract item 7). BFM-only (signal restore on !aresetn) versus proxy-coordinated (also unblocks the waiting sequence with an ABORTED status). The plan proposes both, but the sequence-kill case is UNSETTLED in the record and untested here.
  7. SoC-side propagation ownership (BENCH-065 criterion 1). Outside this repo; needs a named owner in the consuming environment before the VIP-side change is considered "delivered".
